# 逻辑阅读：三技能内化与语义阅读地图技术方案

日期：2026-09-21
状态：P1 可用实现已完成，后续阶段待实施。基于现有 React/Vite、React Flow、FastAPI、SQLite 实现与《阅读技能技术文档》。

## 当前实现范围（2026-09-21）

- 导入后的原文继续按 `books → versions → chapters → paragraphs` 保存，地图生成不会修改段落文本。
- 导入只保存目录和原文，并生成“全书问题 → 章节”的空地图；用户选择某一章并手动执行拆分后，才调用模型、把带 `paragraph_id` 来源的标题保存为 `unit_sets / reading_units / reading_unit_paragraphs`。地图投影为“全书问题 → 章节 → 阅读单元 → 原文依据”。没有可靠来源标题时，整章作为一个单元保留，不按字数强切。
- 每个单元建立“原文、这段在说什么、论述结构、可继续追问”骨架，其中只有原文自动填充，其他栏位留作后续阅读工作流。
- 阅读页支持选中同一段原文后写批注。后端以 `paragraph_id + start_offset + end_offset + quote` 作精确校验，选区与原文不一致会拒绝保存；原有段落笔记保持兼容。
- 已完成后端单元/批注接口测试、前端构建和 Playwright 浏览器回归。冷读复核、多轮修订、复杂章节边界规划、跨段批注和 Markdown 导出仍按下文分期实施。

## 1. 目标与关键决策

把 book-ingest、chapter-split、annotate 转为应用内部的可恢复工作流。模型承担内容理解、命名、边界建议、冷读；程序承担原文搬运、范围校验、存储、版本和地图构建。

地图主干固定为：书 → 卷/篇（若存在）→ 章 → 阅读单元标题 → 原文段落。阅读单元标题直接来自已审核的 chapter-split 结果，不再另行生成一套观点标题。标题命名可以是场景、问题、论证回合，不要求叙事类书籍都转换为论点。

保留单页缩放、拖动、展开和定位。点击单元在右侧打开阅读面板，点击段落定位原文和批注；可进入独立阅读页。段落层按需展开，避免全书几千段一次渲染。导读放在章节详情中，九段笔记骨架放在单元阅读页。

数据库作为唯一运行时事实来源，Markdown 是可重建的导出产物。复用技能的规则与确定性算法，不依赖用户机器上的技能目录或运行中的 Codex。应用内独立冷读是一条独立模型调用链，无需部署 Codex 子代理。

## 3. 内部模块

```text
React 页面 → FastAPI API → SQLite 工作流队列 → 独立 worker
                           │                    ├─ ingest：探测/章节规划/覆盖校验
                           │                    ├─ segmentation：结构图/落缝/冷读
                           │                    ├─ validation：原文与锚点硬校验
                           │                    └─ map_projection：标题投影为地图
                           ├─ annotations：选区校验/批注/进度
                           └─ export：Markdown 兼容包
worker → ModelGateway → OpenAI 兼容 / Anthropic Messages
```

建议模块目录：`app/workflows/`、`app/ingestion/`、`app/segmentation/`、`app/annotations/`、`app/exports/`、`app/prompts/`。现有服务继续运行，新增数据库迁移编号，不靠 CREATE TABLE IF NOT EXISTS 处理字段升级。

## 4. book-ingest 内化

1. 上传并计算源文件 SHA-256，保留源文件；创建 staging 导入任务。
2. 提取格式、目录树、spine、锚点、标题、页码和正文块。EPUB 优先结合 TOC 锚点与正文；Markdown 识别标题层级；TXT 综合标题序列与内容；PDF 结合书签和正文，不按页直接成章。
3. PDF 按页记录文本密度，疑似扫描型停止；混合型缺文页标为待处理，不能宣称全书完整。首版不提供 OCR。MOBI/AZW 系列通过可隔离的格式适配器支持，无可读文本或格式不支持时明确失败。
4. 模型输出受限 ChapterPlan：标题、父子结构、起止 source_block_id、排除区间及理由。由程序切片，模型不输出整章 body，不执行模型生成的 Python。这是把一次性切分脚本改成声明式边界计划的产品化替代。
5. 程序校验边界有效、顺序、覆盖、重复、空章。主体与显式排除区间必须恰好覆盖源块一次；排除项可在导入报告查看和恢复。
6. 源文件与不可变标准正文存妥后，事务提交章节、段落、报告。失败只保留草稿与诊断，不混入正式书架数据。

标准正文是格式提取后的确定文本，保留段落分隔与字符映射；“无损”限定为相对此标准正文。HTML/PDF 到文本的视觉、排版损失单独报告，不能把正文哈希一致说成原文件字节一致。

## 5. chapter-split 内化

### 5.1 工作流

分诊 → 完整章结构分析 → 单元边界与标题草案 → 程序提取候选原文 → 独立冷读 → 按反馈修订 → 再审（最多两轮冷读）→ 严格校验 → 发布单元与地图。

切分遵循注意力、语义自足、信息密度。短章可为单单元，建议产品统一经过一次冷读，消除原技能短章分支与冷读必需之间的歧义。超两轮仍有关键缺陷时置为 needs_review，不自动宣称通过；用户仍可阅读原文章节。

独立冷读只接收候选标题、按序完整切片、稳定引用标识和五问；不能接收切分理由或切分者对话。可以用相同模型但必须新上下文，记录 reviewer_prompt_version、模型、轮次、输入摘要与结果。不同模型可配置，非必需。

五问逐单元返回：是否完整、首尾是否悬空、是否混合不相干内容、是否密度过高、相邻是否应合并。程序检查反馈引用的单元/边界存在；切分者据此生成新草案后重新切片，冷读者不直接修改原文。

### 5.2 超长章处理

输入预算只决定传输窗口，不决定阅读单元。按原始顺序覆盖所有窗口并保留重叠上下文；生成带源范围的局部结构记录，再汇总全章结构图。所有候选边界需用边界两侧原文复核，可以跨窗口合并。冷读按单元及相邻单元提供全文；若单个单元超过上下文，分窗口遍历并保存审查覆盖账本，再汇总检查，不用摘要代替未读正文。预算或上下文不足时明确未完成，不静默截断。

### 5.3 草案契约（示意）

```json
{
  "chapter_id": "ch_x",
  "source_revision": "src_v1",
  "chapter_hash": "sha256:...",
  "genre": "narrative",
  "intro": "本章阅读导引",
  "units": [
    {
      "draft_id": "u1",
      "title": "第一次会谈：从抱怨别人到面对自己",
      "start_paragraph_id": "p1",
      "start_anchor": "第一段开头的原文",
      "purpose": "这段在讲什么",
      "independence_reason": "为何能独立阅读",
      "density_note": "长但场景连续，因此保留"
    }
  ]
}
```

首版以自然段边界为最小粒度；paragraph_id 消除重复原句歧义，start_anchor 必须与该段开头精确匹配。长且复杂的单段若需要段内切分，后续扩展原句+字符范围，不由长度强切。

### 5.4 硬校验

首边界必须对应完整章正文起点；边界严格递增且不重复；末尾隐式覆盖章末；单元非空；每个段落恰属一个单元。原文通过标准正文的连续范围切片，不经模型重写；所有切片拼接后与完整章正文逐字符一致、哈希一致。发布后重读持久化范围再次验证。

### 5.5 九段骨架

一原文：程序读取范围；二字词注、三白话直译、四注家对照、五前章/前单元连接、六三个问题、七生活关联：待生成；八你的理解/疑问、九回看批注：留白。

不能在拆分阶段自动填满二至七，八九只能记录用户实际输入。注家对照需真实来源，无来源的模型解释应叫分析视角。完整陪读聊天是独立后续功能，不冒充三个技能已有能力。

## 6. 标题如何成为逻辑地图

地图节点 title 直接读取已发布 reading_units.title，node_id 使用单元稳定身份映射；修改标题同时更新地图显示，不重新调用模型。每个 unit 节点绑定正文范围、阅读状态、批注数和九段骨架。

边分三类：contains 表示包含；next 表示阅读顺序；可选 argument/narrative 关系表示有原文依据的因果、转折、例证或场景转换。默认只展示 contains，next 可开启；标题相似或先后顺序不能证明 supports/causes。可选关系需要来源范围与 author/inferred 标签，失败不阻塞主地图。

示例（标题仅演示，不是该书实际生成结果）：

```text
书名
└─ 第一章
   ├─ 设问：这个问题为何出现
   │  └─ 原文第 1–5 段
   ├─ 推演：两个选择会带来什么
   │  └─ 原文第 6–12 段
   └─ 收束：作者如何回应起初的问题
      └─ 原文第 13–16 段
```

全书模式后台顺序/有限并发处理所有章节；按章阅读模式仅拆当前章，其余章节点显示待拆分。已通过章即可在同一画布阅读，不等待整书完成。地图提供全书概览、当前章定位、标题搜索、路径面包屑；大量段落使用按需加载与虚拟化。

## 7. annotate 内化

用户选中文字 → 前端记录 paragraph_id、source_revision、start/end、quote → 后端验证正文版本与精确子串 → 写 annotations → 页面高亮 → 点击查看/编辑批注。

锚点必须落在原文，不能匹配九段骨架的解释区。跨自然段选区拆成多条 anchor，使用 annotation_group_id 关联同一笔记事务。重复句由 paragraph_id+offset 定位，不猜匹配结果；quote/prefix/suffix 用于核对与迁移提示。首版统一以 Unicode code point 偏移，前端将 UTF-16 DOM 选区转换为 code point，并测试 emoji 与组合字符。

批注存储独立于原文；类型为独立解释或概念指针，作者明确 user/model，不默认署名 Claude。请求幂等键防重复提交；合法的再次批注允许显式新建。AI 草稿由用户保存后成为笔记，跨段保存全成功或全失败。

导出生成 NN.notes.md 的 callout。Web 高亮由 App 实现，不依赖 Obsidian 插件；在 Obsidian 里高亮仍需对应插件。

## 8. 数据设计

| 表 | 关键字段与用途 |
|---|---|
| source_revisions | book_version_id、源文件哈希、canonical_text 路径/哈希、提取器版本 |
| source_blocks | revision_id、稳定序号、正文范围、源文件/DOM/页码位置 |
| import_plans / exclusions | 章节方案、排除区间、理由、探测与覆盖报告 |
| segmentation_versions | chapter_id、source_revision、状态、prompt/model、父版本、active 指针 |
| reading_units | segmentation_version_id、稳定身份、ordinal、title、start/end paragraph、正文范围/哈希 |
| unit_sections | unit_id、section_no 2–9、body、状态、author、revision；原文不复制进可编辑区 |
| review_runs | 方案哈希、轮次、独立冷读输入摘要、反馈、是否通过 |
| annotations / annotation_anchors | 笔记正文/署名；revision、paragraph、offset、quote、group |
| workflow_steps | job_id、类型、输入哈希、状态、attempt、租约、heartbeat、输出引用、错误码 |
| reading_progress | user_id、source_revision、paragraph 完成状态；单元进度由范围聚合 |

现有 books/book_versions/chapters/paragraphs 可扩展复用；nodes/relations 保留旧观点图及新图投影，增加 map_kind=claims|units，避免旧数据混成新语义单元。原 notes 迁移为段落级批注，quote 为该段全文，保留 ID、作者与时间。

## 9. 任务恢复与模型调用

独立 worker 从 SQLite 事务领取持久任务，HTTP 只排队；进程重启后回收过期租约并续跑。单步骤幂等键含 source hash、输入计划 hash、prompt version、model config fingerprint（不得包含明文 Key）。成功检查点可复用，失败章/批次重试，无需重跑整本书。

模型调用前不持有数据库写事务。调用完成后先校验，再短事务保存；这也解决当前 generation.py 在章节事务里进行网络调用的问题。

progress 同时记录当前章、窗口、冷读轮次、实际已完成/总步骤。50% 停留时显示具体工作而非假递增。总步骤动态增加应明确；失败报告可定位章、步骤和原因。

网关先检查 HTTP、响应内容类型、stop_reason/finish_reason 是否截断，再提取文本与 schema 校验。截断不得用补括号伪造成成功；JSON 修复仅处理字符串外尾逗号等不改变含义的问题，保留诊断。格式失败最多一次修正请求；超时/限流限次退避；必要时缩小传输窗口，但重新审查语义边界。达到重试预算置 failed/review_required，不能承诺永不失败。

目前正则删尾逗号可能改变字符串内文本，改为理解 JSON 字符串状态的修复器。原始响应仅受控短期诊断留存，不在用户页面输出书稿、Key 或完整堆栈。

保留现有两种 API 格式。模型配置默认仅内存；如要重启自动恢复，增加明确的“在本机记住 Key”，通过系统钥匙串保存。工作流恢复时凭据缺失进入 waiting_for_credentials，不降级成本地假解析。

## 10. API 草案

统一保留 `/api/v1` 前缀：

- POST /books/upload：创建导入任务，返回 202 与 job_id。
- GET /books/{id}/import-report：探测、章计划、排除项与校验结果。
- POST /chapters/{id}/segmentation-runs：创建按章切分任务；全书入口创建父任务。
- GET /chapters/{id}/units：返回已发布单元与草稿处理状态。
- GET /units/{id}：原文范围、九段骨架、批注与进度。
- GET /books/{id}/map?kind=units：从已发布单元投影地图。
- POST /annotations：创建带精确 anchors 的批注；PATCH/DELETE 对应修改与删除。
- POST /jobs/{id}/retry：只重试失败/中断步骤，复用已验证输出。
- POST /jobs/{id}/cancel：停止后续调用，保存检查点。
- GET /jobs/{id}：步骤与等待状态；首版轮询，后续 SSE。
- POST /books/{id}/exports：创建兼容 Markdown ZIP 导出任务。

校验错误返回结构化 code、chapter_id、step_id、可重试标记，不暴露 Python traceback。

## 11. 版本、重拆分与 Markdown 导出

原文 revision 永不原地覆盖。已有二至七解读或任何用户笔记的章节，禁止普通覆盖重拆，返回保护状态。显式重拆创建候选新版本，展示差异并保留旧版本；批注依旧锚在原文段落上，只重建单元归属。无法无歧义迁移的内容留在旧版本并提示，不能丢弃。读取进度以原文为依据，重拆不重置。

导出结构：books/书名/源文件、progress.md、chNN/raw.md、00-导读.md（多单元）、01.md…、01.notes.md。另加 manifest.json 保存稳定 ID、hash、版本与完整性报告。目录名严格净化，书名冲突用稳定 ID 消歧。

在 staging 目录完整生成、重新读取原文区验证，再打包/原子发布。Markdown 不和数据库双向同步；若未来支持 Obsidian 回导，单独设计冲突与版本协议。

## 12. 分期实施与验收

P1 数据与导入：引入 schema migration、不可变标准正文、源块/章节边界计划、覆盖门槛、旧数据兼容。

P2 语义拆分与地图：结构分析/边界计划/独立冷读/校验、单元表、unit 地图和单元阅读页；持久工作流及断点续跑与本阶段一起交付。

P3 批注与导出：精确选区、跨段事务、九段骨架编辑保护、Markdown ZIP 与写后验证。

P4 可选增强：陪读讨论、带证据的跨单元逻辑关系、Obsidian 回导；不作为三个技能内化的前置条件。

必须验证：

1. 同文档多章 EPUB、TOC 与正文分离、重复标题、混合型 PDF 不丢正文或误把目录当完整章节。
2. 长而连贯单元不机械切碎；短而密集单元可独立；冷读收到真实原文而非切分理由。
3. 首段漏掉、边界重复/逆序、空单元、缺段、多段、版本不符一律拒绝发布。
4. 单元切片拼回完整标准正文逐字符一致，落盘/持久化后再验证。
5. 单元标题与地图节点一一对应；章节顺序不自动标为因果/支持。
6. 重复句、emoji、跨段选区正确高亮；原文 hash 在批注前后不变。
7. 重启、超时、截断、限流和重复提交可恢复；重试不重新计费已完成步骤（仅复用已有成功结果，服务端已处理但客户端未获响应的请求无法保证不重复计费）。
8. 已深读章节不覆盖；重拆后旧批注和进度仍可访问；失败新版本不替换已发布版本。
9. 全书生成耗时、每阶段调用数/token、失败率和首次可读章节时延有实际测试记录，不预先承诺固定耗时。
